Chalk Runner · reconnect

Two tabs, one seat

The server holds a dropped player's seat for twenty-five seconds, and reconnect survived every phone, cable and lock screen I threw at it. Then two tabs on one laptop turned out to be one player.

Waseem Ahmad Ansari

Chalk Runner is a two-seat game. One person draws the ground, the other runs on it, and if either of them drops out the round stops dead. On a phone that happens constantly: the network flickers, the screen locks, somebody takes a call. So the server holds a dropped player's seat open for twenty-five seconds. Each player gets a secret key when they join, the browser remembers it, and on reconnect the client offers the key back:

if (m.key) {
  const back = this.players.find(x => x.key === m.key);
  if (back) {
    if (back.ws && back.ws !== ws) back.ws.close(1000, 'replaced');
    back.ws = ws; back.gone = 0;
    send(ws, { t:'you', id: back.id, name: back.name, key: back.key, back: true });
    return;
  }
}

Refresh the page mid-round and you are back where you were, still the drawer, still with your chalk. I tested it by refreshing, by pulling the network cable, by locking a phone and unlocking it. It worked every time.

Then I tried to play against myself

The obvious way to try a two-player game on your own is two tabs. Tab one joins and becomes the drawer. Tab two opens the same link, and instead of joining as the second player it takes tab one's seat. Tab one's socket closes with 'replaced', its canvas freezes, and the room now contains one player who thinks they are two.

I had stored the seat key in localStorage.

localStorage is scoped to an origin, not to a tab. Every tab on the same site reads and writes the same box. So tab two started up, found a key sitting there, and did exactly what I had told it to do: offered the key, claimed the seat, evicted the previous socket. The reconnect logic was not broken. It was working perfectly on a false premise — that a key in storage belongs to this client.

Why none of my tests caught it

This is the part worth sitting with. I had a headless test harness that ran two clients through a whole round, and it never came close to this.

The harness modelled each client as its own object with its own fake storage. Two clients, two storages, two keys. That is a faithful model of two people on two laptops, and it is precisely wrong about two tabs on one laptop, which is how nearly everyone tries a browser game for the first time.

The test double was more isolated than reality. Every other kind of test double I had written that day erred the other way — sharing something the real thing would not share — and I had been watching for that. I was not watching for a stub that granted my code an isolation the browser does not actually provide.

The fix, and why it is better than a workaround

One word: sessionStorage.

It is scoped to the tab. It survives a refresh, which is the case reconnect exists for. It does not survive closing the tab, which is correct — a closed tab is not coming back, and holding its seat for twenty-five seconds would only make the next player wait.

The alternative I nearly reached for was to keep localStorage and key it by something per-tab, generating an id on load and namespacing the entry. That works, and it is a workaround: it reimplements tab scoping on top of a store that deliberately does not have it, and the next person to touch the file has to work out why. sessionStorage is not a trick. It is the store whose lifetime already matches what the data means.

What I take from it

Check the lifetime, not just the API. Browser storage is usually chosen for how long it lasts. It is also worth asking who else can see it, because "the same browser" and "this tab" are different answers and only one of them is what a seat key means.

Play it on one machine. Multiplayer bugs hide in the configurations nobody designs for. Two tabs, two windows, one phone hotspotting the other, the same person joining twice by accident. None of those are in the spec and all of them happen in the first five minutes a real person has with the thing.

Ask what your fakes are quietly promising. A test double does not only stand in for behaviour, it stands in for scope. Mine promised isolation that the real runtime never offered, and every test I wrote on top of it inherited the promise.
